## Project

Family Budget Tracker (FBT) is a web information system where a family records money movements, sees balances, sets monthly budgets and savings goals, and views reports. It is a university team project for *Basics of Information Systems*.

**The requirements in `docs/` are the source of truth.** Read the relevant document before implementing a feature, and do not invent behaviour that contradicts it. If the docs are unclear or seem wrong, say so and ask. Do not guess.

## Core domain rules (never break these)

1. **A transaction is not an expense.** Every transaction has exactly one type: `INCOME`, `EXPENSE` or `TRANSFER` (BR-01).
2. **Account fields depend on type** (BR-03 – BR-05):
   - `INCOME`: destination account + income category, no source account.
   - `EXPENSE`: source account + expense category, no destination account.
   - `TRANSFER`: source + destination (must be different), **no category**.
3. **Transfers are never counted** in income totals, expense totals, category reports or budgets (BR-12, BR-15). They change only the two account balances.
4. **Amounts are always positive** (> 0, max 2 decimals). Direction comes from the type and accounts, never from a minus sign (BR-02).
5. **Balance** = opening balance + incoming (INCOME, TRANSFER in) − outgoing (EXPENSE, TRANSFER out), excluding soft-deleted rows (BR-07).
6. Cash, bank card and savings accounts cannot go below 0; credit cards cannot go below −credit limit (BR-08).
7. Transaction date cannot be in the future (BR-09).
8. Budgets apply only to expense categories, one per category per month, and count only `EXPENSE` transactions including subcategories (BR-14, BR-15). Alerts fire once at 80 % and once at 100 % (BR-16).
9. Refunds are `INCOME` in the "Refunds" category and do not reduce budgets (BR-28).
10. Deletion of transactions is **soft** (`is_deleted = true`) and must write an audit entry. Audit log is append-only (BR-11, BR-27).

## Security and access (enforce on the server, not only in the UI)

- Roles: `OWNER`, `ADULT`, `CHILD` (per family) and system administrator. Follow the permission matrix exactly (NFR-02).
- Every query must be scoped to the current user's family. A user must never read or change another family's data (NFR-03).
- A Child sees and uses only accounts shared with them, can record only `INCOME`/`EXPENSE`, cannot edit or delete, and never sees the family total (BR-10, BR-13).
- Hash passwords with bcrypt or Argon2; never log passwords or tokens (NFR-01).
- **No email in v1** (decision D-3). Invitations use a copyable link + in-app pending invitation; password reset is a one-time link generated by the system administrator. Do not add email sending.

## Data and database

- Database: **PostgreSQL** (decision D-4).
- Money: `numeric(14,2)` in the database and a decimal type in code. **Never use float/double for money** (NFR-08).
- Timestamps: `timestamptz`; audit values: `jsonb`.
- Name the table `transactions` (plural): `transaction` is a reserved word.
- Saving a transaction and updating any cached balance must happen in **one database transaction** (NFR-09).
- Follow names, enums and constraints from `docs/07-data-dictionary.md`. Change the schema only through migrations.

## Code and testing conventions

- Put business rules (validation, balance, budget calculations) in a service/domain layer, not in views or UI components, so they can be unit-tested.
- Every business rule you implement needs at least one test. Name tests after the IDs, e.g. `test_br05_transfer_requires_two_different_accounts`.
- The worked example in `docs/06-business-rules.md` must pass as an automated test.
- Use the exact user-facing error messages from the use cases where given (NFR-15).
- Show money as `125 000,00 ₸` (NFR-20).

## Git workflow

- Never commit directly to `main`. Use branches: `feature/US-08-record-expense`, `fix/...`, `docs/...`.
- Commit messages: `type: short description (IDs)`, e.g. `feat: record transfers between accounts (FR-18, US-10)`.
- Open a pull request, link the issue (`Closes #N`), and get one review before merging (NFR-19).
- Never commit secrets, `.env` files or real personal data.

## When requirements change

Do not silently change behaviour that the docs define. Tell the Systems Analysis & Requirements owner so `docs/` is updated (new version + change-log entry in `docs/README.md`).
